# Contributing

Use the linked live tool first, then describe the problem, the version, what you expected and what actually happened. Include a small invented example and the checks you ran. A proposal can also explain an access barrier or suggest clearer wording.

Keep file inventories, personal documents, private messages, credentials and participant details out of issues and patches. Use made-up examples. Say when a result is simulated or a check has not been performed.

Keep changes small and explain how to undo them. Maintainer review precedes changes to the working website. A proposed patch does not publish itself or establish that a tool is suitable for a particular person.

Please preserve the existing privacy choices, authorship, permission statements and limits. Public wording should use plain language and ordinary punctuation. If a change affects a hashed script or stylesheet, rebuild and verify its Content Security Policy hashes before a release.
